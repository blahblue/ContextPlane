# ContextPlane Security Validation Checklist

This checklist is adapted from the Outpost security validation checklist and the launch/security/performance checklists supplied during the 2026-10-02 review. Outpost-specific surfaces such as chat, voice, Electron, uploads, invites, minors, payments, and social moderation are excluded unless ContextPlane later adds an equivalent surface.

Security is a continuous PR requirement, not a one-time launch exercise.

## PR start rule

For every security-relevant PR:

1. Review this checklist before implementation.
2. Mark relevant controls Applicable, Not Applicable, or Follow-Up.
3. Implement Applicable controls in the same PR unless an explicit dependency prevents it.
4. Add negative/adversarial tests for trust boundaries.
5. Re-run applicable checks after implementation.
6. Do not merge with a known unresolved Critical or High finding.
7. Never treat an LLM prompt, MCP tool description, client-supplied selector, hidden client behavior, cache entry, or URL shape as an authorization boundary.

The core ContextPlane property is:

> A principal must never receive, infer, resolve, audit, or reuse context belonging to another tenant or unauthorized identity merely by changing request fields, selectors, identifiers, transport, or cache state.

## 1. Secrets and configuration

- [ ] No private keys, database passwords, OAuth client secrets, bearer tokens, or service credentials are committed to code, tests, examples, logs, screenshots, or docs.
- [ ] Real secrets are supplied by environment/secret management only.
- [ ] `.env` and local secret files are ignored.
- [ ] Git history is scanned for leaked secrets.
- [ ] CI secret scanning is enabled.
- [ ] Production credentials are distinct from development/test credentials.
- [ ] Error messages do not expose configuration or credentials.
- [ ] Exposed secrets are rotated; deleting a commit is not considered remediation.

## 2. Authentication

- [ ] Protected REST and remote MCP surfaces authenticate on the server.
- [ ] JWT signature, issuer, audience, expiry, issued-at, tenant, subject, and client identity are validated.
- [ ] Accepted algorithms are pinned.
- [ ] Ambiguous user/agent/service identity fails closed.
- [ ] Authentication errors are generic.
- [ ] Production key rotation/JWKS behavior is defined.
- [ ] IdP session lifetime, revocation, MFA, and Conditional Access responsibilities are explicit.

## 3. Authorization and tenant isolation

- [ ] Tenant identity comes from the authenticated principal, never request input.
- [ ] Every tenant-scoped database lookup includes the authenticated tenant.
- [ ] User/agent/client-scoped lookups include all required identity dimensions.
- [ ] MCP helper tools cannot widen their fixed domain through model input.
- [ ] Repository/resource/task/audience selectors are applicability inputs, not authorization credentials.
- [ ] Cross-tenant and cross-principal adversarial tests exist.
- [ ] Permission changes cannot reuse stale cache state.
- [ ] Database-level isolation is used where it materially reduces blast radius.

## 4. Database security

- [ ] SQL is generated by SQLAlchemy or parameterized statements.
- [ ] User-controlled input is never concatenated into SQL.
- [ ] Database credentials follow least privilege.
- [ ] Production Postgres is not publicly exposed.
- [ ] TLS is required for production database connections.
- [ ] RLS is evaluated for tenant-bearing tables; if not used, the rationale and compensating controls are documented.
- [ ] Foreign keys/check constraints preserve tenant/logical integrity where possible.
- [ ] Sensitive fields are minimized and encrypted at rest by the deployment platform where appropriate.
- [ ] Backups and restore testing are operational requirements.

## 5. Input validation and injection prevention

- [ ] External request models use explicit schemas and reject extra fields.
- [ ] IDs, strings, collections, enum values, timestamps, URLs, and list sizes are bounded.
- [ ] Client input cannot override tenant, subject, principal kind, roles, groups, scopes, audit actor, authority metadata, or server-fixed domains.
- [ ] No shell/process execution receives model/user input.
- [ ] Remote fetch features, if introduced, protect against SSRF and unsafe schemes.
- [ ] Context text remains data and cannot acquire authority through imperative wording.

## 6. HTTP/API perimeter

- [ ] HTTPS is mandatory in production.
- [ ] Sensitive API responses are marked non-cacheable by shared caches.
- [ ] Security headers are set where applicable: HSTS on HTTPS, `X-Content-Type-Options`, frame protection/CSP, referrer policy, and permissions policy.
- [ ] Production API docs/schema exposure is intentional.
- [ ] Error responses do not expose stack traces, SQL, paths, topology, or secrets.
- [ ] APIs return only required fields.
- [ ] Expensive requests have size/count limits.
- [ ] Health endpoints reveal only minimal liveness information.

## 7. Rate limiting and abuse resistance

- [ ] Authentication/token-validation paths have an edge or application rate limit.
- [ ] Resolve/audit endpoints are rate-limited or protected by an equivalent gateway control.
- [ ] Limits cannot be bypassed using model-controlled selectors.
- [ ] Expensive requests are bounded independently of frontend/client behavior.
- [ ] Multi-instance deployments document where distributed throttling is enforced.

## 8. Caching

- [ ] Cache keys include every authorization-relevant identity dimension.
- [ ] Cache keys include policy/version state and applicable selectors.
- [ ] Context updates invalidate or bypass stale entries.
- [ ] Time-based applicability cannot outlive an effective-date boundary.
- [ ] Private context is never placed in a shared public cache.
- [ ] HTTP cache headers match response sensitivity.

## 9. Audit and logging

- [ ] Security-relevant runtime outcomes generate audit records.
- [ ] Denied authenticated requests are audited without copying sensitive payloads.
- [ ] Audit reads are principal/tenant protected.
- [ ] Ordinary application flows cannot edit/delete audit history.
- [ ] Bearer tokens, raw context payloads, secrets, and unnecessary selector values are omitted from audit/log records.
- [ ] Production logs distinguish operational diagnostics from security/audit history.
- [ ] External WORM/SIEM retention is evaluated for production.

## 10. Dependencies and software supply chain

- [ ] New dependencies are justified.
- [ ] Unused dependencies are removed.
- [ ] Known-vulnerability scanning runs in CI.
- [ ] Dependency update automation is enabled.
- [ ] Locking/pinning strategy is documented for deployable artifacts.
- [ ] CI actions are pinned to immutable commits.
- [ ] CI permissions are least privilege.
- [ ] Package sources are trusted.
- [ ] High/Critical dependency findings block release unless explicitly risk-accepted.

## 11. Resilience and failure modes

- [ ] Token-validation failure denies access.
- [ ] Policy/configuration ambiguity fails closed.
- [ ] Database failure does not return stale unauthorized data.
- [ ] Cache failure cannot widen authorization.
- [ ] Retry logic does not duplicate sensitive state changes.
- [ ] Security errors remain observable through safe correlation/audit identifiers.

## 12. Privacy, legal, accessibility, and user control

The supplied launch checklist includes privacy policy, terms, cookie consent, form consent, data minimization, third-party SDK disclosure, dark-pattern/hidden-fee review, unsupported claims, accessibility, business details, age consent, unsubscribe links, asset licensing, and deletion requests.

For the current ContextPlane repository:

- cookie/banner/session-cookie controls: **N/A** — no browser session/cookie auth;
- refunds/hidden fees/fake reviews/marketing unsubscribe: **N/A** — no commerce or marketing surface;
- minors/age consent: **N/A** — ContextPlane is enterprise infrastructure, not a child-directed account product;
- frontend accessibility/alt text/color contrast/keyboard navigation: **N/A** — no end-user UI;
- fonts/images licensing: **N/A** for runtime code; review if product UI/assets are later added;
- privacy policy/terms/business operator details: **deployment/product-owner responsibility before a hosted public service is launched**;
- data deletion/retention: **Applicable to hosted deployments** because context and audit data can contain enterprise identifiers; retention and deletion policy must be defined before production launch;
- third-party processors: **Applicable** for Entra, hosting/database providers, and any future source connectors.

## 13. Performance checklist adapted from the supplied launch review

Security-safe performance expectations:

- [x] SQLAlchemy connection pooling is used.
- [x] tenant/key and tenant/logical database indexes exist for core lookup paths.
- [x] expensive candidate resolution has a bounded in-process cache.
- [ ] request collection sizes and maximum returned-context size are explicitly bounded.
- [ ] N+1/query-count regressions are measured for larger corpora.
- [ ] load balancer/CDN/compression policy is defined for production deployment where relevant.
- [ ] production load tests establish throughput/concurrency targets.

Frontend-only items such as image compression, skeleton loaders, code splitting, browser re-render optimization, minified JS/CSS, lazy loading, and Lighthouse are currently **N/A**.

## Merge-blocking conditions

Do not merge with a known unresolved:

- authentication bypass;
- cross-tenant or cross-principal context disclosure;
- privilege/authority escalation;
- exposed private credential;
- SQL/command injection;
- fail-open token/policy behavior;
- shared-cache private-data leakage;
- audit actor/tenant bypass;
- High/Critical dependency vulnerability with practical exposure and no documented mitigation;
- missing server-side validation for a security-sensitive input.

## PR security review block

Every security-relevant PR should record:

- feature/surface;
- sensitive data touched;
- trust boundaries crossed;
- authentication/authorization assumptions;
- applicable checklist sections;
- threats considered;
- controls implemented;
- negative/adversarial tests;
- residual risks and follow-ups;
- result: PASS / PASS WITH FOLLOW-UP / BLOCKED.
